# Impeccable — Portable Design Workflow

Brainforge adaptation of Impeccable 4.3.1, modified for provider-neutral,
project-scoped work. See [NOTICE.md](NOTICE.md) and [LICENSE](LICENSE).
This is a portable design procedure, not the complete upstream plugin engine.

## Choose the work

Read the assigned task, saved product decisions, existing interface and available
assets. Reuse settled facts. An ordinary design request is sufficient; a slash
command is optional text, not an installed command-line program.

- **New surface or requested redesign:** read
  [references/design-workflow.md](references/design-workflow.md).
- **Critique, audit, polish or a focused improvement:** read
  [references/quality-review.md](references/quality-review.md).
- **Record or update the design system:** use the documentation section in
  [references/design-workflow.md](references/design-workflow.md).
- **Bare `/impeccable` with no goal:** suggest two or three useful actions based
  on the actual project, such as planning a page, reviewing the current design
  or improving a named screen. Do not begin an unrequested redesign.

Load only the relevant reference. Small copy, spacing or state fixes do not need
a new product interview, a visual direction workshop or new design documents.

## Design contract

The user's goal, confirmed content and explicit visual commitments govern the
work. Distinguish refinement from redesign: refinement preserves the current
identity; redesign replaces its visual expression while retaining product truth,
function and constraints. Missing design documentation alone does not make an
existing interface a blank slate.

Choose the surface's purpose: persuade someone to act, help someone operate a
tool, explain something to a reader, or let someone experience an artifact.
Use that purpose to decide composition, density, imagery and interaction. A
product's marketing page and its administrative screens can need different modes.

Produce a recognizable direction from the audience, subject and supplied assets.
Avoid default card grids, decorative statistics, interchangeable hero sections
and unnecessary visual effects. Familiar patterns are appropriate when they
serve the user's brief; a stylistic preference is not a universal prohibition.
Do not invent claims, prices, testimonials or business facts to fill a layout.

## Host and evidence boundaries

Brainforge owns roles, permissions, task dispatch and review. This skill does not
create agents, select model names, authorize account changes or grant tools.
Research and review tasks return text; only an authorized build task persists
design documents or edits the assigned files. Preserve the host's output schema.

Check the tools available in this run before promising screenshots, image
generation, browser interaction or application execution. Use the host's managed
preview and browser tools when present. A procedure or an installed skill does
not establish a connected Canva account, an image service or a running browser.
If a required visual check cannot run, name it as unavailable; source inspection
is useful evidence but is not a rendered visual pass.

This adaptation omits the upstream executable, automatic detector, randomized
concept engine, decision-page server, live element selector, hooks and native
agent installers. Do not invoke upstream `impeccable` commands or download tools
on the assumption that this skill installed them. Use available host tools and
the references here; report a requested unsupported feature explicitly.

## Finish without an open-ended polishing loop

Build the authorized scope, inspect the relevant desktop and mobile views in one
batch, correct the material findings in one batch, then confirm once. Additional
work follows a concrete unresolved finding and the host's repair budget; do not
restart a general defect hunt. Pass actual evidence to the host's reviewer when
available. Never describe a self-review as an independent review.

Report the files or deliverables, the chosen direction, checks actually executed,
remaining findings and unavailable checks. Keep development briefs and internal
review notes out of browser-delivered HTML, hidden DOM and public assets.
