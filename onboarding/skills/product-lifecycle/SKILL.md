# Deliver the product through its lifecycle

The current assistant owns coordination. Use the user's outcome and existing
work to choose the next stage. A small fix or one marketing asset does not
require restarting this lifecycle. Do not build the proposed voice supervisor
or a cross-client runtime as part of following this procedure.

## Keep one delivery record

Read the four workspace memory files. Create or update
`workspace/output/delivery-plan.md` with the agreed outcome, success evidence,
scope, constraints and a small milestone table. Each milestone has an owner,
dependencies, next action, status and evidence link. Use `planned`, `active`,
`blocked`, `verified`, or `not-needed` with a reason. Separate product work,
release work and marketing work; they can have different completion states.
Link the record from next.md rather than duplicating it in memory.

Choose only applicable stages. Ask about the product in everyday language,
one material question at a time, and reuse prior answers. Do not ask the user
to staff the team or choose internal procedures. Discover detail as it becomes
relevant instead of conducting a long interview before the first result.

| Stage | Produce and verify | Procedure or responsibility |
| --- | --- | --- |
| Problem and audience | First user journey, intended audience, useful result, evidence versus assumptions | Market strategy when research is needed; coordinator for known requirements |
| Product and design | Smallest useful scope, interaction sketch, acceptance examples, accessibility needs | Solution design and appropriate interface/game specialist |
| Architecture and team | Reasons for technology choices, existing constraints, scoped assignments | Solution design; capability expansion for uncovered work |
| Implementation | Working vertical slices, real storage/integrations where required, error states | Selected software packs; actual project tests |
| Quality and readiness | Acceptance evidence, access boundaries, performance relevant to the user, remaining defects | Reviewer and release operations |
| Release | Versioned release, observed deployment or store status, rollback route, operator notes | Release operations |
| Acquisition | Positioning, landing content, creative assets, channel plan and authorized campaign preparation | Relevant marketing procedures below |
| Operation and learning | Support path, observations, metrics, prioritized improvements | Customer feedback and campaign analysis |

Marketing research and drafts can proceed before implementation finishes.
Claims about product behavior must match delivered or explicitly upcoming
features. Promotion must not claim the product is available before release.
Payments, accounts, sensitive data, offline support and multiplayer appear
only when the actual product needs them.

## Route work by missing capability

Read [the specialist index](../../SPECIALISTS.md) and only selected skills.
Before a task that cannot be completed with available capabilities, run
[capability expansion](../capability-expansion/SKILL.md). For supported roles,
use the native activation instructions in the index. Reuse builders and
reviewers for small work; do not create one agent for every stage.

For marketing, use the relevant sequence, not necessarily every step:
[market strategy](../market-strategy/SKILL.md),
[brand and copy](../brand-copy/SKILL.md),
[creative production](../creative-production/SKILL.md),
[content and SEO](../content-seo/SKILL.md),
[paid campaigns](../paid-campaigns/SKILL.md), then
[campaign analysis](../campaign-analysis/SKILL.md).
Use [release operations](../release-operations/SKILL.md) for distribution and
[customer feedback](../customer-feedback/SKILL.md) for operation and retention.

## Continue through the authorized outcome

Close each milestone with actual evidence, route defects to their owner and
continue the next unblocked authorized task. Do not stop at a plan when the
user requested implementation. Do not run every specialist in parallel:
settle shared contracts first and separate write ownership.

If an external account, asset or decision is missing, identify the exact blocked
step, request only what is needed and complete independent work. Never substitute
a simulated integration for a required real one without clearly agreeing on
the reduced scope. Keep secrets out of shared memory and generated profiles.

Before external publication or spending, finish the reviewable artifact and
check existing authorization for the exact account, destination, scope and
budget. Ask only for missing authorization, not for work already approved.
Record observed status afterward. A prepared release is not deployed; a store
submission is not approval; campaign setup is not evidence of delivery or sales.

Finish with delivered outcomes, supporting checks, live versus local status,
and any remaining dependency. Update the delivery record and next action.
